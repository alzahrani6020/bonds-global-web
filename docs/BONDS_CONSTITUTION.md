# دستور منصة BONDS — BONDS Platform Constitution

> **الإصدار:** 1.0-draft  
> **الحالة:** وثيقة أساسية لكل تطوير قادم  
> **الهدف:** تحويل BONDS من موقع إلكتروني + حاسبات منفصلة إلى منصة عالمية متكاملة لاتخاذ القرار الاستثماري والتقييم الاقتصادي.

---

## 1. الرؤية الواحدة (One Vision)

**BONDS ليست موقعاً ولا مجموعة حاسبات.**

BONDS هي **منصة ذكاء اقتصادي متكاملة (Investment Decision Intelligence Platform)**.

### الهدف الأساسي
مساعدة المستثمر والإدارة والبنوك والشركات والأفراد على اتخاذ **القرار الصحيح** بسرعة، اعتماداً على:
- بيانات حية وموثقة.
- محركات خبرة متخصصة.
- تحليل ذكي.
- تقارير احترافية.
- شهادات رقمية قابلة للتحقق.

### المبدأ الذهبي
> المستخدم يركز على **اتخاذ القرار**، والمنصة تتولى تلقائياً: جمع البيانات، التحليل، المقارنة، المحاكاة، التقييم، التمويل، التقارير، الشهادات، والمتابعة.

## 2. مبادئ التصميم المعماري (Architectural Principles)

### 2.1 لا يوجد "حاسبات" بعد اليوم
- كل أداة سابقة تُسمى **محرك خبرة (Expert Engine)**.
- المستخدم لا يشعر بوجود المحرك؛ يشعر فقط بنتيجة قرار أو توصية.
- لا توجد صفحات عنوانها "حاسبة X" أو "Calculator X".

### 2.2 كل شيء يبدأ بالنية (Intent-First UX)
- أول سؤال للمستخدم دائماً: **"ما الذي تريد تحقيقه؟"**
- النظام يحدد تلقائياً:
  - نوع المشروع.
  - نوع الأصل.
  - نوع الدراسة.
  - نوع التقييم.
  - نوع التمويل.
  - نوع التحليل.
  - نوع التقرير.
- ثم يبني الرحلة تلقائياً.

### 2.3 BONDS Intelligence Core — العقل المركزي
- يوجد **نواة ذكاء مركزية** تنسق جميع المحركات.
- أي تعديل في أي قيمة ينشر تلقائياً إلى كل المحركات المتأثرة.
- لا يُسمح بمحرك معزول لا يتواصل مع النواة.

### 2.4 طبقة بيانات موحدة (Unified Data Layer)
- كل بيانات المستخدم تُخزن مرة واحدة فقط.
- جميع الوحدات تقرأ وتكتب من/إلى نفس المصدر.
- يُمنع تكرار إدخال البيانات أو وجود نسخ متعددة.

### 2.5 Live Data Engine
- يجلب البيانات الحية من المصادر الموثوقة:
  - بيانات اقتصادية ومالية.
  - بيانات عقارية وتجارية وصناعية.
  - بيانات سوق ومنافسين وأسعار.
  - بيانات حكومية وتنموية وديموغرافية.
  - بيانات بيئية (طقس، مخاطر طبيعية) عند الحاجة.
- كل بيانة يجب أن تحمل:
  - المصدر.
  - تاريخ الالتقاط.
  - درجة الثقة.
  - تاريخ انتهاء الصلاحية.

### 2.6 Smart Data Override
- يمكن للمستخدم تعديل أي بيانة مستوردة.
- عند التعديل:
  - يُسجل السبب.
  - يُعاد الحساب تلقائياً.
  - يُحسب أثر التعديل.
  - يُعرض الفرق بين بيانات السوق وبيانات المستخدم.

### 2.7 AI Decision Analyst
- لا يكتفي النظام بعرض النتائج.
- بعد كل عملية، يُنتج تقريراً احترافياً يوضح:
  - أسباب ارتفاع/انخفاض القيمة.
  - المخاطر والفرص.
  - أفضل قرار.
  - أفضل وقت للبيع/الشراء/التمويل/التطوير/التخارج.
  - أفضل طريقة لزيادة القيمة وخفض المخاطر.

### 2.8 Digital Twin
- كل أصل أو مشروع أو شركة له **ملف رقمي دائم**.
- يُحدث النظام الملف تلقائياً عند تغير السوق أو البيانات.
- لا تبدأ الدراسات من الصفر؛ تبدأ من الملف الرقمي.

### 2.9 Decision Graph
- كل قرار داخل النظام يعرف أثره على بقية النظام.
- عند تغير قيمة، تظهر جميع النتائج المتأثرة.

## 3. النموذج المعرفي للمنصة (Domain Model)

### الكيانات الأساسية

| الكيان | التعريف | أمثلة |
|---|---|---|
| **User** | الشخص الذي يستخدم المنصة. | مستثمر، مصرفي، مستشار، شركة. |
| **Project** | عملية استثمارية أو قرار اقتصادي قيد الدراسة. | مصنع، مطعم، عقار، شركة. |
| **Asset** | عنصر ذي قيمة يتم تقييمه. | عقار، معدات، شركة، علامة تجارية. |
| **Valuation** | تقييم قيمة الأصل بمنهجيات متعددة. | تقييم عقار، تقييم مصنع. |
| **Financing** | هيكل التمويل المناسب للمشروع. | قرض، شريكة، تمويل مختلط. |
| **Scenario** | سيناريو محاكاة مالي أو سوقي. | متشائم، متوقع، متفائل. |
| **Report** | مخرج تحليلي قابل للطباعة والمشاركة. | تقرير جدوى، تقرير تقييم. |
| **Certificate** | وثيقة رقمية موثقة وقابلة للتحقق. | BDVC، شهادة جدوى. |
| **Knowledge** | المعرفة القطاعية والتنظيمية. | معايير القطاع، الأنظمة، أفضل الممارسات. |
| **DataSource** | مصدر بيانات خارجي موثوق. | World Bank، KAPSARC، بيانات حكومية. |

### العلاقات
- **User** يملك عدة **Project**.
- **Project** يحتوي على عدة **Asset**.
- **Asset** يمتلك **Valuation** واحد أو أكثر.
- **Project** يمتلك **Financing** و**Scenario** و**Report** و**Certificate**.
- جميع الكيانات مرتبطة بـ **Knowledge** و**DataSource**.

## 4. تصنيف المحركات (Engine Taxonomy)

كل محرك يُعرف بالمسؤولية التالية:

| المحرك | الوظيفة | أمثلة |
|---|---|---|
| **Valuation Engine** | تقييم الأصول بمنهجيات متعددة. | realEstate، business، factory. |
| **Feasibility Engine** | دراسة الجدوى الاقتصادية. | مشاريع جديدة، توسعات. |
| **Risk Intelligence Engine** | تقييم وقياس المخاطر. | مخاطر سوقية، تنظيمية، تشغيلية. |
| **Market Intelligence Engine** | بيانات السوق والمقارنات. | أسعار، طلب، عرض، منافسة. |
| **Financing Engine** | هيكلة التمويل والجدارة الائتمانية. | قرض، DSCR، مخاطر ائتمانية. |
| **Cashflow Engine** | التدفقات النقدية والاستدامة. | projections، break-even. |
| **Condition Assessment Engine** | تقييم حالة الأصول المادية. | معدات، عقارات. |
| **Depreciation Engine** | حساب الاستهلاك بأنواعه. | محاسبي، اقتصادي، تقني. |
| **AI Analyst Engine** | كتابة التحليل والتوصيات. | تقارير تنفيذية، SWOT. |
| **Certificate Engine** | إصدار وتحقق الشهادات الرقمية. | BDVC. |
| **Live Data Engine** | جلب وتحديث البيانات الحية. | أسعار، مؤشرات، بيانات حكومية. |
| **Knowledge Engine** | توفير السياق القطاعي والتنظيمي. | معايير، أنظمة، دروس. |
| **Decision Graph Engine** | رسم أثر القرارات على النظام. | ما يتأثر عند تغير قيمة. |

### قواعد المحركات
1. كل محرك يُصدر **نتيجة موحدة** (standard output schema).
2. كل محرك يُعلن **متطلباته** من البيانات مسبقاً.
3. كل محرك يُعلن **درجة ثقته** في النتيجة.
4. المحرك لا يُعدّل بيانات المحركات الأخرى مباشرة؛ يُبلغ النواة.

## 5. معمارية البيانات (Data Architecture)

### 5.1 المستويات

| المستوى | الوظيفة | التقنية |
|---|---|---|
| **Raw Data** | البيانات الخام من المصادر. | Supabase + external APIs. |
| **Master Data** | البيانات المعيارية والمصححة. | Supabase tables. |
| **Project Data** | بيانات المستخدم والمشروع. | Supabase + local draft. |
| **Computed Data** | النتائج المحسوبة من المحركات. | In-memory + cached in DB. |
| **Knowledge Data** | المعرفة القطاعية والتنظيمية. | JSON/DB. |

### 5.2 قواعد البيانات
- لا يُسمح بتكرار جدولين يخزنان نفس المعنى.
- كل جدول يحمل تعليقاً (comment) يوضح دوره.
- كل عمود يحمل تعليقاً يوضح وحدة القياس ومصدره.
- جميع التغييرات تمر عبر ترحيلات (migrations) مرقمة.

## 6. تجربة المستخدم (UX Architecture)

### 6.1 رحلة المستخدم الموحدة
1. **Intent:** ما الذي تريد تحقيقه؟
2. **Discovery:** تحديد نوع المشروع/الأصل/القرار.
3. **Data:** جمع البيانات مرة واحدة.
4. **Analysis:** تشغيل المحركات المناسبة.
5. **Insight:** عرض التحليل والتوصيات.
6. **Decision:** اتخاذ القرار بناءً على النتائج.
7. **Documentation:** إصدار التقرير أو الشهادة.
8. **Monitoring:** متابعة المشروع/الأصل عبر Digital Twin.

### 6.2 مبادئ الواجهة
- لا قوائم رئيسية تقليدية.
- لا صفحات حاسبات منفصلة.
- كل شاشة تخدم قراراً واحداً.
- التصميم يعتمد على الوضع الداكن بشكل افتراضي.
- يجب أن تكون جميع الشاشات responsive و accessible.

## 7. الهوية البصرية الموحدة (Design System)

### 7.1 نظام الألوان
- **الذهبي:** `#D4A853` — التمييز والثقة.
- **الخلفية الداكنة:** `#0A0F1A` — الوضع الافتراضي.
- **بطاقات داكنة:** `rgba(16, 24, 45, 0.6)`.
- **النص الرئيسي:** `#E8ECF4`.
- **النص الثانوي:** `#94A3B8`.
- **الحدود:** `rgba(197, 160, 40, 0.15)`.

### 7.2 الخطوط
- العربية: `Vazirmatn` ثم `Cairo`.
- الإنجليزية: `Inter` أو `system-ui`.

### 7.3 الشعار
- الشعار الحالي مؤقت.
- يجب إنشاء شعار عالمي جديد يعبّر عن: الذكاء، الترابط، الثقة، القرار، البيانات، الاستثمار، التقييم، النمو.
- يجب أن يكون بسيطاً، سهل التذكر، قابلاً للاستخدام في جميع الوسائط.

### 7.4 المكونات
- شبكة تصميم ثابتة (8px grid).
- مسافات موحدة.
- أزرار موحدة (Primary / Outline / Danger).
- بطاقات موحدة.
- نوافذ منبثقة موحدة.
- رسوم بيانية موحدة.

## 8. حوكمة التطوير (Development Governance)

### 8.1 قاعدة منع الميزات الجديدة
> **لا تُضاف أي ميزة جديدة قبل التأكد من توافقها مع هذا الدستور ومعمارية المنصة.**

### 8.2 أي ميزة جديدة يجب أن:
1. تكون جزءاً من النظام المركزي.
2. لا تُنشئ صفحة أو محركاً منفصلاً.
3. تستخدم طبقة البيانات الموحدة.
4. تتواصل مع BONDS Intelligence Core.
5. تُنتج نتيجة موحدة.
6. تُحدّث Decision Graph.
7. تُخضع للاختبارات والتدقيق.

### 8.3 قائمة التحقق قبل أي تطوير
- [ ] هل هذه الميزة تخدم قراراً استثمارياً واضحاً؟
- [ ] هل تستخدم البيانات المخزنة مسبقاً؟
- [ ] هل تتواصل مع المحركات الأخرى؟
- [ ] هل تحدّث Digital Twin؟
- [ ] هل تُنتج تقريراً أو توصية؟
- [ ] هل تم اختبارها على الجوال؟
- [ ] هل تم اختبار accessibility؟
- [ ] هل تم تحديث الدستور إذا لزم الأمر؟

## 9. التقارير والشهادات (Reporting & Certificates)

### 9.1 التقارير
- كل تقرير تفاعلي وقابل للتصدير.
- يُخصّص التقرير حسب الجهة المستفيدة:
  - المستثمر.
  - البنك.
  - الجهة التنظيمية.
  - الإدارة العليا.
- يتضمن مصادر البيانات ودرجات الثقة.

### 9.2 الشهادات
- كل شهادة رقمية تحمل:
  - رقم فريد.
  - ختم تشفيري (HMAC-SHA256).
  - QR Code للتحقق.
  - تاريخ إصدار وانتهاء.
- يمكن التحقق منها علنياً.

## 10. الأمن والامتثال (Security & Compliance)

### 10.1 أمن البيانات
- لا توجد أسرار (API keys) في الواجهة الأمامية.
- جميع العمليات الحساسة تتم عبر API موثق.
- RLS مفعّل على جميع الجداول.
- التوثيع عبر Supabase Auth + JWT.

### 10.2 الامتثال
- احترام لوائح حماية البيانات.
- توثيق مصادر البيانات.
- إخلاء مسؤولية واضح في كل تقرير.
