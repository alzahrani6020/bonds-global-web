# Generated Artifact and Repository Retention Policy

Status: Active repository-hygiene policy. The generated feasibility PDF cleanup was completed after CI reproducibility and reference gates passed.

## Principles

1. Do not delete an artifact unless runtime/reference dependency has been ruled out with adequate evidence.
2. Generated artifacts may be removed from Git only when regeneration is reproducible from a clean checkout with declared dependencies.
3. Database-affecting maintenance scripts are treated as operational or historical records until an explicit owner confirms retirement.
4. Backups and snapshots require an explicit retention rule before deletion.
5. Deletions must be isolated in a dedicated cleanup PR, pass CI, and retain a clear rollback path.

## Large PDF decision

Both generated feasibility PDFs were removed from Git in PR #337 after all safety gates passed.

### Verification completed

- both generators run from a clean checkout with declared Playwright dependencies;
- `npm run verify:feasibility-pdf` generates and validates both PDFs;
- `npm run audit:generated-pdfs` scans repository text sources and fails on unexpected references;
- the only filename false positive was the client-generated jsPDF download name in `calculator-wizard.js`, which does not consume a repository binary;
- `.gitignore` prevents both generated binaries from being recommitted;
- full CI passed before merge;
- production deployment from the cleanup merge commit reached READY;
- both former production PDF paths return 404 after deployment;
- no runtime errors were observed in the post-deploy verification window.

Current decision: **REGENERATE ON DEMAND; DO NOT VERSION THE BINARIES IN GIT**.

## Backup retention

The existing `BACKUP_STRATEGY.md` specifies off-site retention for database dumps but does not define retention for `v3/master-data/backup/`.

Until a separate master-data retention rule is approved:

- preserve all existing snapshot directories;
- do not treat age alone as a deletion criterion;
- document the snapshot creation workflow before pruning;
- require confirmation that current master-data files can restore the same state or that the snapshot has no audit value.

## Legacy and maintenance scripts

The four reviewed scripts are not ordinary dead code. They can modify production-like database state and therefore have audit and recovery value even when they are not referenced by `package.json`.

Current policy:

- keep them in source control;
- do not expose them as casual package scripts;
- document database/environment prerequisites before execution;
- consider moving them to a clearly named historical/maintenance directory only in a separate PR after confirming no runbook or external automation depends on the paths.

## Safe deletion gate

A file can move to DELETE-CANDIDATE only when all are true:

- no runtime, build, deployment, documentation, release, or operational dependency remains;
- the owning workflow or team confirms it is retired;
- legal/audit/backup retention does not require it;
- regeneration or recovery is verified where applicable;
- the cleanup PR is narrow and reversible.
